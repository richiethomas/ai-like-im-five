Neural networks are sensitive to the scale of their inputs, and pixels come in a wide range: 0 to 255.

Recall from Part 8 that the size of the input feeding a weight is one of the things that sets how much that weight gets adjusted: bigger inputs tend to mean bigger adjustments. Raw pixels run all the way up to 255, big enough to make those adjustments large and erratic, so training is unstable and slow.

The fix: **normalize** the inputs, shrinking them to a small, consistent range.

## Normalization

The simplest approach: divide every pixel by 255, so the values run from 0 to 1 instead of 0 to 255.

```
normalized_pixel = raw_pixel / 255
```

Now every input is between 0 and 1 instead of up to 255: small, comparable numbers for the network to work with.

A more thorough approach is **standardization**. Dividing by 255 only shrinks the numbers; standardization also re-centers them around zero.

```
standardized_value = (raw_value - average) / standard_deviation
```

Subtract the average and divide by the **standard deviation** (a measure of how spread out the values are), both measured on your training data and then applied unchanged to any new data. This puts the values around zero with a comparable spread. Inputs that are centered and evenly scaled make training easier for gradient descent, which the next section explains. Networks generally train more easily this way.

## Why This Matters

Pixels all live on the same 0-to-255 scale, so a single division by 255 shrinks them into a small range together. It gets trickier when a model's features are on different scales from each other, because then no single divisor works for all of them.

Say a model predicts a house's value, and one house has two features:

- Bedrooms: 4
- Square footage: 2500

From Part 8, the gradient for a weight (the number that sets how far it moves) is the blame arriving at it (its share of the error) times the feature it multiplies. With the same blame, 1, reaching both weights:

```
bedrooms weight's gradient       = 1 × 4    = 4
square footage weight's gradient = 1 × 2500 = 2500
```

The square-footage weight's gradient is over 600 times bigger, not because square footage matters more, but only because it is counted in bigger numbers than bedrooms. Each step moves a weight by the learning rate times its gradient, so with one learning rate for both, the square-footage weight lurches while the bedrooms weight barely moves. One rate can't serve both, so training stalls or thrashes.

Standardization (from the start of the post) fixes this. For each feature, it measures that feature's own average and spread (a.k.a. its standard deviation, the distance a typical value sits from the average). Then it subtracts the average and divides by the spread.

Suppose bedrooms average 3, with most houses within about 1 of that (a spread, or standard deviation, of 1), and square footage averages 2000, with most homes within about 1000 of that:

```
bedrooms standardized       = (4 - 3) / 1          = 1
square footage standardized = (2500 - 2000) / 1000 = 0.5
```

They both come out near 1 by design, not by coincidence: that is the whole job of standardization, pulling every feature onto a common scale no matter what size it started at. Dividing everything by one number, the way we divided pixels by 255, wouldn't do this, because bedrooms and square footage are on different scales; each needs its own average and spread. Now the gradients are comparable:

```
bedrooms weight's gradient       = 1 × 1   = 1
square footage weight's gradient = 1 × 0.5 = 0.5
```

so the two weights move at similar rates, and a single learning rate works for both. That is the point of normalizing: put every input on a comparable scale, so no weight is updated wildly harder than another just because its input happened to be bigger.

The difference shows up during training: with normalization the loss drops fast and smoothly; without, it falls slowly and wobbles as the mismatched updates fight each other.

## Beyond Pixels

Normalization isn't only for pixels. Whenever your inputs arrive on very different scales, the same problem shows up and the same fix helps:

- Financial data (prices from $1 to $10,000)
- Fitness data (daily step count in the thousands, next to hours of sleep, 0 to 12)

Here each feature is standardized using its own average and standard deviation, so no single feature dominates just because its numbers happen to be bigger. (Inputs already on a small, similar scale need less of this.)

A common guideline: when your features sit on very different scales, put them on a common one before training.
